# 项目仓库扫描预算

创建扫描时可选文件尝试上限 50、100、200 或 500，及累计读取上限 1、5 或 10 MiB。默认值为 200 文件和 5 MiB。服务端严格校验这些选项并保存到 `project_scans`；服务重启后按该任务的原配置继续。旧扫描迁移时记录原先的默认值。

文件上限统计纳入扫描的 blob，包括[从先前扫描复用的正文](project-scan-reuse.md)；排除的依赖、构建、二进制或敏感文件不占用次数。总读取量按本次纳入扫描的正文大小计算，复用正文也占预算；已经下载并检测为敏感内容的文件同样计入。单文件仍限制 256 KiB，目录补读上限 100 次，索引最多 5,000 项。文件数用尽标记 `unscanned/file_budget`，预计字节数超上限标记 `unscanned/byte_budget`；旧记录的 `unscanned/scan_budget` 保持为未区分原因，不推断是哪一种。提高预算需要新建一次扫描，旧扫描及其报告不改写。

公开与私有 GitHub API 的单次响应均限制为 32 MiB。递归目录响应超限时，扫描改为分层读取；单个子树响应仍超限时记录为未展开子树，根目录无法读取则扫描失败。分层读取的已保存索引最多 5,000 项，额外目录项计入未扫描数量，待处理子树队列也有上限。索引不完整时不凭缺失路径推断旧文件已删除；报告保留部分覆盖提示。
目录索引完整性单独保存为 `project_scans.index_complete`。文件数、字节数预算用尽可能导致扫描部分覆盖，但已索引路径仍可完整；这时同路径的 Git SHA 变化和已确认的路径增删仍可比较。目录响应、索引项或子树上限导致索引不完整时，跨扫描差异只写入能够由两侧索引证明的变化。

扫描详情按原因汇总未读数量、最多五条示例路径，以及未进入索引的目录项和未展开目录数；表格保留逐文件原因。报告还区分扫描阶段未读文件与可读文件因分析选择上限未进入模型的数量。部分覆盖时的“未发现”只适用于进入模型的范围，不能据此推断整个仓库。

增量扫描会用同仓库、同分支上一份扫描的路径与 Git blob SHA，把已索引且 SHA 改变的文件放在读取队列前部；只有上一份扫描覆盖完整时，才把旧索引中不存在的新路径也视为新增文件优先读取。已变化文件最多占本次文件数及总字节预算的一半。扫描器还用上一份扫描中已读取的源码建立静态依赖图，把可识别的引用方和直接依赖文件放入第二优先队列；该队列最多占文件数及总字节预算的四分之一。其余文件继续按目录和文件类别轮流分配。排序只改变预算内读取机会，不增加读取上限，也不保证所有变化或相关文件都被读取；“全量重扫”同样可使用此排序，但不会复用旧正文。

相同仓库、commit 的排队或扫描中任务仍会合并。若第二次提交使用不同预算，接口返回已存在任务及其实际保存的预算；完成后可再按新预算发起扫描。预算限制读取量，不保证 GitHub API 限流、网络失败或目录截断不会造成其他未扫描范围。

扫描记录列表按 `created_at DESC, id DESC` 稳定排序，一次返回 20 条和下一页游标。页面每 4 秒刷新最近一页的状态，同时保留用户已经加载的旧记录；“加载更多”沿游标读取较早扫描。文件正文仍通过单条扫描的权限校验后按需读取，列表不返回正文。
