# 项目分析调用恢复与费用边界

每个分析作业在调用模型期间持有 PostgreSQL 会话级 advisory lock，同一个作业不能由两个 API 进程同时调用。每个目录模块在发出请求前写入 `project_analysis_module_calls.started`；模型返回后，原始输出、用量和费用记录在一个数据库事务中改为 `completed`。重启后，已完成的模块使用保存的输出继续汇总，不再调用供应商。`analysis_plan_version` 在创建作业时固定调用计划：旧作业使用版本 1，仅按模块调用；新作业使用版本 2，满足证据条件时额外调用一次跨模块综合。跨模块调用使用独立的调用键，并遵循相同的预算预留、结果保存与重启恢复规则，因此升级后不会给旧作业补发一笔模型请求。

如果进程在请求发出后、结果入库前退出，数据库只知道调用已开始，无法判断供应商是否实际执行或收费。该作业以 `CALL_OUTCOME_UNKNOWN` 失败，**不自动重发**；页面提示管理员，手动重试前需确认可能再次计费。迁移前处于 `analyzing` 的旧作业也按此口径标为失败，不伪称可安全恢复。取消已发出的请求不能保证供应商不收费。

新建分析、预览私有代码发送范围和手动重试时，扫描的可信 GitHub 仓库 ID、分支与 commit 必须和当前项目配置一致；重试还要核对原作业的目标和需求版本。提交事务重新读取并锁住当前项目配置，变化后拒绝创建或重试，避免对已失效扫描继续产生模型费用。已保存报告仍可按原快照查看和对照。

这一机制防止并发执行、重复入账和重启后的无提示自动重调，但不能提供跨供应商的严格“恰好一次收费”。若供应商以后支持可靠的幂等键，才能把调用结果未知的时间窗进一步收窄。作业取消、失败重试次数、状态、错误码、用量与报告仍由现有 `project_analyses` 和 `project_analysis_attempts` 持久化。
