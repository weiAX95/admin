# 项目分析建议的人工确认

报告固定可信 GitHub 仓库身份、分支、commit、项目目标和需求基线。报告与原扫描的仓库、分支和提交必须一致，并与当前项目配置匹配。任一条件不满足，尚未处理的建议在读取时呈现为「已失效，需重审」；任务差异预览、接受及个人调整接口均拒绝继续操作。迁移前缺少可信仓库 ID 的扫描报告保留阅读能力，须重新扫描和分析后才能转为任务。历史上已经接受或忽略的决定保持原样；重复读取已接受结果不再次写入任务，旧建议仍可被忽略。

页面在当前 commit 有已完成扫描、原模型仍可用时提供「重新分析当前扫描」。此操作会再次调用模型并可能产生费用；否则应先扫描当前 commit 或选择可用模型。新报告有自己的建议 ID 和证据，旧报告及人工校正记录继续保留。

生成新报告后，可在“两次报告对照”逐条重审旧建议。新旧报告必须属于同一账号、同一分支和已核对的同一 GitHub 仓库 ID；旧报告须早于新报告。页面并排展示两份报告生成时固定的建议原文（实践与验收标准）、既有接受／忽略决定，以及新报告中的候选建议；后续个人调整不改变这份对照依据。稳定需求 ID 和词面相似度只用于排列候选，不自动认定两条建议等价。用户可确认对应新建议、标记需跟进，或说明旧建议已不适用；每次确认保存理由、账号、时间与并发版本。新报告若已不再匹配当前项目目标、需求版本或 commit，历史重审可读，但不能再写入过期结论。缺少可信仓库身份、跨分支或报告与扫描提交不一致时，仍可查看有限对照，但不会请求逐条建议复核。

重审记录独立于建议接受／忽略决定。已忽略的旧建议不会自动恢复；确认配对也不会替用户接受新建议、创建任务或覆盖人工进度。需要执行新建议时，仍由用户在新报告中按原有确认流程操作。旧报告及其代码证据始终保持固定；重审只保存人工认定的关系和理由。

新建议会与同一账号、同一仓库中已接受且任务仍存在的建议比较主题与实践文本，最多展示三条相关任务链接。相似度使用归一化字符双字片重合率，阈值为 0.55；它只帮助人工核对措辞相近的建议，不理解语义，也不能保证找到所有同义建议。主题和实践均完全相同的建议由服务端唯一约束阻止再次转任务；近似项仍需用户判断，系统不会自动覆盖或合并现有任务。

同一报告中，前置知识与另一条建议的主题经 NFKC、大小写及标点空白归一后唯一匹配时，页面先展示前置建议，并列出该明确关系。同级建议按模型估计影响排序。名称重复时不推断依赖；模型给出循环关系时提示人工核对，剩余条目按影响排序。其他前置知识仍显示原文，不被伪装为已识别的建议依赖。

用户也可以选择“关联已有任务”。页面先调用预览接口，展示任务描述的原值、追加后的完整值和新增部分；确认时提交预览取得的任务版本。服务端在锁定当前项目配置的事务中重新检查可信仓库身份、分支、扫描来源、目标、需求版本、commit、任务权限和版本，再追加来源与验收文字、记录字段变更历史及活动，并建立仓库任务关联。任务标题、状态、进度、优先级等字段不修改；版本过期时拒绝写入，要求重新预览。已处理建议重复提交保持原决定，不能改指向另一任务。决定中的 `target_mode` 区分新建任务与已有任务，旧接受记录迁移为“新建”。
