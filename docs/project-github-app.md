# GitHub App 账号授权：当前交付边界

分析计划第 11 版会把同账号、同仓库及分支中有限数量的既有已接受建议摘要发送给模型，以提示可能重复的学习任务。私有仓库的发送范围预览现在列出这些候选的任务标题、主题、实践和验收文字；确认摘要覆盖完整候选快照，候选变化时必须重新预览。模型判断只供人工核对。

当前 `/project-analysis` 新增账号连接入口。管理员先在 GitHub 建立 GitHub App，设置用户授权回调为同源的 `/api/project-github/callback`，仅申请仓库 Metadata read 与 Contents read，并启用会过期的用户访问令牌。服务端配置 `GITHUB_APP_CLIENT_ID`、`GITHUB_APP_CLIENT_SECRET`、`GITHUB_APP_CALLBACK_URL` 与独立的 `GITHUB_APP_MASTER_KEY`。本地开发启动命令会生成主密钥；正式环境应由密钥管理系统提供，API 和后续扫描 worker 使用同一密钥。主密钥轮换可通过版本和旧密钥映射读取旧记录，完成逐条重加密后再移除旧密钥。

连接流程生成 256 位随机 `state` 和独立的 256 位浏览器标记，数据库只存两者的 SHA-256。浏览器标记作为十分钟有效的 HttpOnly、SameSite=Lax Cookie，只发往回调路径；HTTPS 回调附加 Secure。回调同时核对 `state` 和浏览器标记，二者都匹配后才能将 GitHub 身份绑定到发起授权的管理端账号；状态仅可使用一次。[123_project_github_browser_binding.sql](../db/migrations/123_project_github_browser_binding.sql) 使旧的待完成授权状态失效。GitHub 授权码只在服务端交换。服务端用用户访问令牌读取 `/user` 验证 GitHub 身份，并以 AES-256-GCM 加密保存访问与刷新令牌。加密附加数据绑定管理端账号、字段和密钥版本。状态接口只返回 GitHub 登录名和到期时间；断开连接删除该账号保存的令牌及未完成授权状态。管理端账号删除时通过外键清理凭证。调用 GitHub 前，服务端在访问令牌接近到期时以刷新令牌续期；刷新令牌失效或 GitHub 返回 401 时清除连接，要求重新授权。数据库行锁防止同一账号并发续期互相覆盖。

账号连接不等于已授权任意私有仓库。页面可通过当前账号的用户令牌列出 GitHub App 安装中可访问的仓库；当前最多读取 500 个并标记截断。用户可显式选择其中一个私有仓库登记到项目列表。服务端重新读取 `/repos/{owner}/{repo}`，确认当前用户令牌确实可访问且仓库为私有；登记、分支刷新和所有该仓库的详情请求重新核验权限，失权后列表隐藏该仓库，详情返回拒绝。公开仓库仍按原有无凭证路径读取。私有仓库扫描前后再次核验权限，读取树和 blob 均带当前账号的 App 用户令牌，禁用旧正文复用；授权失效会终止扫描并拒绝保存结果。正在进行的 GitHub HTTP 请求持有数据库共享锁，断开连接要等待这些请求结束；断开返回后不再启动新的私有读取。主动断开还会在同一事务中关闭本账号私有仓库的自动扫描／分析，并把未启动的待确认分析标为跳过。令牌失效或刷新期限到期后，服务启动时及每分钟清理一次缺少有效连接的私有自动配置和待确认队列；清理独立于正在进行的 GitHub 请求，以免与 Webhook 处理器持有的仓库锁互等。GitHub 回调中的 `installation_id` 不作为权限凭据。断开本系统连接只删除本系统凭证；若需撤销 GitHub App 在 GitHub 的安装授权，还须在 GitHub 设置中操作。

新接入项目保存 GitHub 返回的不可变仓库 ID；此后的私有读取、固定 commit 扫描和 Webhook 处理均核对该 ID。仓库改名但 ID 不变时，可刷新为 GitHub 当前名称；旧名称若被其他仓库占用，ID 不一致会拒绝读取。旧项目此前只有名称，[141_project_github_repository_identity.sql](../db/migrations/141_project_github_repository_identity.sql) 不会猜测其身份，也不会把历史扫描追认为可信：迁移关闭旧项目的自动扫描／分析，并终止未完成的旧扫描／分析；[142_project_legacy_auto_analysis.sql](../db/migrations/142_project_legacy_auto_analysis.sql) 跳过已完成旧扫描仍待处理的自动分析。所属账号须在页面预览当前仓库 ID、分支和 commit，确认确为原项目后绑定。绑定后需重新扫描才能生成新报告；历史报告保留供查看，但不能作为新扫描的缓存或可比进度基线。旧私有项目在完成核对前也不能接受跨账号的学习证据审核。

私有扫描完成后，提交分析前先预览固定 commit、扫描预算、将送入模型的文件摘录路径、模型名称与提供方、实际连接目的地。页面确认后提交预览摘要；服务端按同一扫描、当前项目目标与需求正文、摘录内容哈希及目的地重新计算摘要，不一致时要求重新预览。确认记录保存在 `project_analyses.private_disclosure`（[122_project_private_analysis_disclosure.sql](../db/migrations/122_project_private_analysis_disclosure.sql)）；凭证和文件正文不写入该记录。私有分析禁用跨分析输出复用；worker 读取扫描正文之前、每次模型调用之前及报告保存之前复核 GitHub 权限，模型目的地变化则失败。模型调用期间持有当前账号 GitHub 连接的共享锁，断开连接等待该调用结束，之后不再启动下一次调用。仓库正文、注释和需求文档均被系统提示词标注为不可信分析材料，流程不运行仓库脚本。真实 GitHub App 和模型端到端验收仍待配置凭据后统一执行。

对应表为 [120_project_github_connections.sql](../db/migrations/120_project_github_connections.sql) 的 `project_github_oauth_states` 和 `project_github_connections`。两表均以 `owner_id` 外键绑定 `users`，删除账号时级联删除；不与仓库数据建立假外键。[121_project_private_repositories.sql](../db/migrations/121_project_private_repositories.sql) 为仓库行标记 `is_private`，旧仓库默认公开。授权回调必须经前端同源 `/api` 反向代理，以便回到 `/project-analysis`；生产环境应使用 HTTPS。用户令牌只留在服务端，不得写入日志、API 响应或模型输入。

参考 GitHub 官方文档：[用户访问令牌授权](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app)、[令牌续期](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/refreshing-user-access-tokens)、[安装设置 URL 的安全说明](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/about-the-setup-url)。

## 提交事件自动扫描（14.11 的第一段）

GitHub App 的 Webhook URL 设为公网同源 `/api/project-github/webhook`，订阅 `push`，服务端单独配置 `GITHUB_APP_WEBHOOK_SECRET`。接收端先对**原始请求字节**计算 HMAC-SHA256，再使用恒定时间比较核验 `X-Hub-Signature-256`；缺少密钥或签名时拒绝处理。`X-GitHub-Delivery` 保存为唯一交付 ID，重复投递不会重复建扫描；交付记录按审计保留天数清理，清理后极晚的重放仍会受签名及已有扫描检查约束。验签后先持久接收，再由后台处理；HTTP 接收响应中的 `scansQueued: 0` 只代表尚未开始处理，不是最终扫描数量。数据库记录处理状态、尝试次数、最终核验到的分支 commit 和实际排队数。旧交付记录在迁移时视为已处理，不重新执行。

后台只处理用户开启“提交后扫描”的仓库 ID 和分支；事件内的仓库名称只供审计，不作为绑定依据。处理时锁定对应项目，实时读取 GitHub 当前分支 head 并核对不可变 ID；私有仓库还重新核验所属账号的 App 授权。**以当前 head 排队，不直接信任事件中的 `after` 作为最新状态**：乱序到达的旧 push 会收敛到当前 head，force-push 也按当前 head 处理；标签推送、删除分支和未开启的分支不会排队。分支已不存在时保留交付记录但不回退项目。临时读取失败按 1、2、4 分钟退避，最多四次尝试；最终失败的交付可由 GitHub 重新投递同一 ID 后重新入队。已失去私有仓库授权或仓库 ID 不匹配的项目会关闭自动扫描／分析。两分钟内的后续提交只会改写仍处于排队状态、由 Webhook 创建的扫描目标 commit；手动扫描以及已经开始的扫描始终固定原 commit。若首个扫描已开始，后续提交另建扫描。扫描仍受原有预算与私有仓库权限核验约束，重启后交付处理器和扫描队列分别补做。

扫描开关只排队扫描。公开仓库所属账号还可单独开启“提交后自动分析”，选择可用模型，并逐次设定 token 与美元上限、确认持续调用。已完成或部分覆盖的 Webhook 扫描才提交分析；扫描失败、仓库配置关闭、提交已过时显示跳过或失败原因。自动分析复用手动创建的模型权限、连接、每日预算、token 配额、速率限制和敏感输入校验；数据库保证同一扫描最多一条自动分析记录。短时间内仍排队的提交扫描可合并，已开始的扫描保持原 commit。若完整扫描与上一份已分析的完整扫描没有文件变化，且模型、目标、需求和分析计划版本相同，则公开与私有仓库均跳过重复分析并记录原因；私有仓库此时不再产生待确认通知。自动报告完成后，持久通知队列仅与同分支、同需求基线、同目标、完整且同范围的上一报告对照；有完成线索、新缺口或可能退化、新增高影响建议时发送一次通知，无法可靠比较或无重要变化时不发。通知保留“代码证据仍需人工验证”的提示，可直达对应报告。私有仓库可开启“提交后待确认分析”：扫描完成后只创建待审核状态并通知所属账号；每次必须查看固定 commit 的代码范围、模型目的地和费用上限，再明确确认，确认前不会调用模型。关闭配置或断开 GitHub 授权会停止后续待确认任务。真实 GitHub 交付验收仍在 14.11 待办中。接入正式 GitHub App 后须使用真实交付验证签名、分支匹配及重复交付。该入站接收端与 12.5 的对外发送 Webhook 独立。[GitHub 官方验签说明](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries)和[交付最佳实践](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks)是这里的协议依据。
