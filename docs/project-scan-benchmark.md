# 项目仓库扫描量测

2026-10-11 在本机开发环境量测。以下结果只说明指定样本、预算和环境下的表现；不能外推为所有 GitHub 仓库或生产服务器的完成时间。

| 样本 | 预算与来源 | 结果 | 耗时 |
| --- | --- | --- | --- |
| 1 万目录项模拟仓库 | GitHub API 内存响应、零网络延迟；最多索引 5,000 项、读取 200 个 blob，随后写入本机 PostgreSQL | 5,000 条索引入库，200 条已读、9,800 条未扫描，状态为部分覆盖 | 扫描器 9 ms；含 PostgreSQL 入库 1,082 ms |
| 公开 `vitejs/vite` 固定提交 `3b72997d42e7dd2b31898d0e68461e3025e836b6` | 真实 GitHub REST；最多索引 5,000 项、读取 5 个 blob，用于限制公开 API 请求量 | 3,791 条索引，5 条已读、1,158 条排除、2,628 条未扫描、0 条失败，状态为部分覆盖 | 3,401 ms，含 GitHub 网络时间 |

模拟仓库可运行 `npm run benchmark:project-scan` 重复量测。测试同时核对文件索引数量、数据库状态及未扫描计数，不设置脱离设备条件的统一时间门槛。真实仓库的 commit 固定，扫描结果依赖当时的 GitHub 网络状况和公开 API 配额。

**仍需验收：**使用默认 200 文件和 5 MB 总预算在较大公开仓库上完成一轮实际扫描，记录总时长、限流情况、目录截断后的补读以及页面展示；必要时先配置 GitHub 读取凭据以避免公开 API 配额限制。部分覆盖必须保持显式，不得当成完整项目分析。
