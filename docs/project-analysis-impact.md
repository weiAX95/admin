# 增量分析的影响范围

相邻同分支扫描先用完全相同的 Git blob SHA 识别纯改名。改名同时改了正文时，只在旧、新文件均完整读取、扩展名相同、正文不超过 50,000 字符且各有 8–200 条足够长的不同文本行时尝试匹配；重合行占较大一方至少 85%，且同一旧或新文件没有分数相近（相差不足 0.1）的其他候选，才记录为 `renamed` 并保存旧、新路径和 SHA。两侧未配对文件超过各 300 个时跳过正文匹配。结果是保守的静态线索，无法识别较大改动或不可读文件；含重复模板的仓库仍需人工复核。旧路径和新路径都会进入增量影响范围；报告证据始终只取当前扫描正文。

从分析计划版本 4 起，服务读取该扫描保存的新增、修改、删除、重命名记录，在既有 30 个文件、30,000 字符、8 个模块预算内优先选择变化后的当前文件。对 JS／TS 源码，解析字面量相对路径的 `import`、`export ... from`、动态 `import()` 和 `require()`；`.js`／`.jsx`／`.mjs`／`.cjs` 引用可在索引中回退匹配对应 TS 源文件。Python 解析可对应到索引文件的绝对／相对 `import` 与 `from ... import`；Go 根据已读取的 `go.mod` 将本模块 import 路径映射为包内文件，同包文件也视为相关。变化文件直接导入的当前文件可优先提供上下文，并沿反向导入边逐层寻找引用它的当前文件。删除文件没有当前正文，但仍可作为图的目标，找到仍引用它的文件。优先顺序为变化后的文件、距离最近的引用方、再到直接依赖；根目录依赖或构建配置变化时，已索引目录模块均重新分析。

计划版本 5 在上述导入图中再加入明确的 API 路径边：从 `http.get('/notes')`、`fetch('/api/notes')` 等字面量请求，连接到 `pathname === '/api/notes'`、固定前缀路由正则、常见 JS／Python／Go 路由注册。路径按 `/api` 前缀和完整段边界匹配，客户端引用服务端；服务端文件变化时可沿反向边找到客户端，客户端变化时服务端可作为直接上下文。它只表示需要重新检查，不表示接口已经联通或可运行。

计划版本 6 读取扫描中可用的 `tsconfig*.json`／`jsconfig*.json`，解析 `compilerOptions.paths` 与 `baseUrl`，将字面量 JS／TS 导入别名映射到已索引的源文件，再沿同一静态影响图传播。支持精确映射及单个 `*` 通配符，并兼容配置中的注释和尾逗号；优先使用距离源文件最近的配置。配置缺失、未被扫描、`extends` 继承、Vite／Webpack 自定义别名或复杂路径映射不会推断成已知依赖。

计划版本 7 在可读配置内递归解析本地相对路径 `extends`（含本地配置数组），沿用定义 `paths` 的配置位置解析相对目标，并在同一目录有多个配置时保守合并可索引的目标。循环引用、超出仓库、仅位于 `node_modules` 或未扫描的父配置不推断；这仍不是完整的 TypeScript 模块解析器。相对配置路径的归属依据 [TypeScript TSConfig 文档](https://www.typescriptlang.org/tsconfig/#extends)；`paths` 的相对基准依据 [TypeScript 模块解析文档](https://www.typescriptlang.org/docs/handbook/modules/reference.html#relationship-to-baseurl)。私有代码发送预览、提交时的预算与影响范围、后台执行都使用当前计划版本，避免选入正文不一致。计划版本 6 的旧作业继续按其原有的直接配置规则恢复。

`135_project_analysis_plan_versions.sql` 把分析作业的数据库版本约束扩至 1–7。使用第 6／7 版的服务代码前必须执行 `npm run db:migrate`；旧库若仍停留在仅允许 1–5 的约束，新建分析会在入库时失败。迁移不会改写历史作业的计划版本。

计划版本 8 识别任意目录中的已知依赖与构建配置文件变更，保守地让本次已索引目录模块重新分析；这可能增加模型调用，但不会把局部配置变化错判为安全复用。Go 依赖图以已索引的嵌套 `go.mod` 为模块边界：文件无法读取或缺少明确 `module` 声明时，不借用外层模块名猜测跨包依赖；同目录仅连接可读、声明同一 `package` 的 Go 文件，生产源码不依赖 `_test.go`。这些是静态影响线索，不表示编译或测试通过。`136_project_analysis_impact_v8.sql` 允许计划版本 1–8；旧作业继续按保存的原版本恢复。

计划版本 10 还读取扫描中可用的 `vite.config.js`／`.ts`／`.mjs`／`.mts`／`.cjs`／`.cts`，只接受 `export default { ... }`、`export default defineConfig({ ... })` 或 `module.exports = { ... }` 中直接写出的 `resolve.alias`。支持对象形式 `alias: { '@': './src' }` 和数组形式 `alias: [{ find: '@', replacement: './src' }]`；别名和替换值都必须是普通字符串字面量。若当前源码的字面量导入命中这些别名，则将其识别为**目标未确定的别名边**：有扫描变化时不跨报告复用该引用方所在模块及其沿已知反向依赖边可达的模块，并在文件预算允许时优先提供这些引用方作为上下文；其余模块仍可按原规则复用。即使 `tsconfig`／`jsconfig` `paths` 也声明了同一个导入，仍保留这条不确定边，因为两种配置可能指向不同文件；已知的 TypeScript 目标继续用于现有静态图。Vite 官方说明[相对替换值会原样使用，不会自动解析成文件系统绝对路径](https://vite.dev/config/shared-options#resolve-alias)；因此此处不把 `./src` 猜成相对配置文件的精确目标。同层多个可读配置的字面量别名取保守并集；不可读或动态配置不推断，也不借用外层配置猜测。源码中的注释与字符串示例不会被当作导入；词法扫描无法安全解析的源码不建立别名边，属于覆盖缺口；扫描限定 262,144 个字符、20,000 个词法项及 32 层嵌套模板，避免仓库内容耗尽调用栈。失效范围通常限于别名引用方及其调用链，但图上大量模块可达时仍会增加模型调用；扫描预算、未索引文件和运行时插件仍限制覆盖范围。不执行配置文件，不解析变量、模板字符串、函数、展开属性、正则别名或插件注入的别名。`145_project_analysis_vite_alias_v10.sql` 允许计划版本 1–10；旧作业继续按保存的版本恢复。

计划版本 13 在已读取的 `.sql` 文件中识别字面量 `CREATE TABLE`／`ALTER TABLE`／`DROP TABLE` 声明，把 JS／TS、Python、Go 源码里同名的 `FROM`／`JOIN`／`UPDATE`／`INTO`／`REFERENCES` 语句连到该 SQL 文件。新增 SQL 文件时，相关代码可沿反向边进入复查范围；修改或删除 SQL 文件时，当前扫描无法重建被移除的旧表名，因此保守失效所有已索引模块的模型结果缓存。匹配不区分大小写，带 schema 的表名取末段；这是静态文本线索，不能代替 SQL 解析器。若新增 SQL 文件不可读、过大或未识别到表声明，也失效所有模块缓存。新分析需先执行 `149_project_analysis_sql_impact_v13.sql`；旧计划版本 1–12 继续按原规则恢复。
